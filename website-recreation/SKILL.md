# Website Recreation

## Mission

Build or adapt a working website that follows a supplied `DESIGN_SYSTEM.md`, leverages reusable assets from `./design-system-assets/`, and, when provided, uses the reference website as visual evidence for details not fully documented.

Whether recreating the reference site directly or adapting its visual language and architecture for a new client brand, the goal is a high-fidelity, responsive, animated, and accessible implementation—not a static screenshot-only mockup. Preserve the existing project's architecture and conventions unless the user explicitly asks for a new stack or a rewrite.

## 1. Inputs and prerequisites

Expected inputs:
- A `DESIGN_SYSTEM.md` file, or a clear path to one.
- Extracted local assets in `./design-system-assets/` (if previously generated by `design-system-extractor`).
- A target project/workspace.
- A description of the pages, client brand/niche, content, and functionality to build.
- Optionally, the original reference URL.

If the design system is missing:
1. Search the current workspace for `DESIGN_SYSTEM.md` and `./design-system-assets/`.
2. If `DESIGN_SYSTEM.md` is not found, ask the user to provide it or run the `design-system-extractor` skill first.
3. Do not invent a supposedly extracted design system.

If the target project is unclear, inspect the current workspace and summarize what exists before making changes. Ask one focused question only when an essential decision cannot be safely inferred.

## 2. Required browser & media-tool preflight

Before implementation and browser-based validation:

1. **Browser MCP Check**: Inspect the available tool inventory for `chrome-devtools-mcp`, `chrome-devtools`, or an unmistakable Chrome DevTools MCP equivalent. Confirm that the tools are actually callable.
2. **Media Sourcing Tool Check**: Check whether any media acquisition or generation MCP tools (e.g., Unsplash, Pexels, stock media fetchers, or image generation tools), shell tools (`curl`/`wget`), or API keys in environment variables (without exposing secrets) are available if the client needs niche-specific photos or videos.
3. Read the exposed tool descriptions and schemas. Never invent tool names or arguments.
4. If Chrome DevTools MCP is available, use it to open the local development server and, when supplied, the reference website for screenshots, DOM inspection, computed styles, viewport changes, console errors, and animation/interaction tests.
5. If Chrome DevTools MCP is unavailable:
   - Continue implementation if the project and `DESIGN_SYSTEM.md` specification are sufficient.
   - Clearly report that browser-based visual validation could not be performed because the MCP is unavailable.
   - Do not claim screenshot comparison, browser inspection, or successful visual QA.
   - Ask the user to connect the MCP if they want the visual-validation phase completed.
6. Do not install, configure, or modify MCP infrastructure unless explicitly requested and supported by the environment.

## 3. Project reconnaissance — before editing

Inspect the existing project before changing files:

- Identify framework, language, package manager, build tool, routing, and entry points.
- Inspect package scripts and dependencies (including existing UI or animation libraries like Tailwind, Framer Motion, GSAP, Lenis, Lucide, etc.).
- Identify styling approach: CSS, CSS Modules, Sass, Tailwind, CSS-in-JS, component library, etc.
- Inspect existing components, layouts, public assets folders (`public/`, `src/assets/`), fonts, and design tokens.
- Inspect `./design-system-assets/` if present in the workspace to inventory downloaded logos, SVG icons, images, videos, Lotties, and fonts.
- Identify current routes and the app's existing behavior.
- Check for project instructions such as `AGENTS.md`, `README.md`, and relevant configuration.
- Determine whether the project is empty, an existing application, or an established codebase.

Rules:
- Preserve the current stack and package manager.
- Reuse existing dependencies and components where appropriate.
- Do not replace configuration files or rewrite the project wholesale without need.
- Do not delete user files, remove dependencies, reset git history, or overwrite unrelated work.
- Do not expose or copy secrets from `.env` files.
- Before adding a dependency (such as an animation engine documented in `DESIGN_SYSTEM.md`), verify it is needed and compatible with the existing project.
- If the requested implementation conflicts with existing architecture, explain the tradeoff and choose the least disruptive solution.

## 4. Interpret the design system

Read the complete `DESIGN_SYSTEM.md` before implementation.

Create an internal implementation map that connects:
- **Design tokens** → CSS variables (`:root`), Tailwind config, or theme configuration (including colors, gradients, fluid `clamp()` formulas, shadows, and `z-index` scale).
- **Local extracted assets (`./design-system-assets/`)** → Map extracted SVG icons, fonts, decorative shapes, Lotties, and reusable visuals from the **Local Asset Manifest** table (Section 8 of `DESIGN_SYSTEM.md`) into the target project's `public/` or `src/assets/` directory.
- **Typography rules** → Local/remote font loading, fallback stacks, fluid sizing, line heights, and RTL/LTR rules.
- **Layout & layering rules** → Containers, bento/CSS grids, breakpoints, spacing scale, sticky positioning, and `z-index` stacking contexts.
- **Media placement architecture** → Container aspect ratios, `object-fit`, `object-position`, gradient scrims/overlays (`::before`/`::after`), `mask-image`, `clip-path`, `backdrop-filter`, and 3D perspective wrappers.
- **Component specs** → Reusable components, variants, sizes, and interactive states.
- **Animation mechanics ("How It Works")** → Required animation engines (GSAP, Framer Motion, Lenis, Lottie, or CSS `@keyframes`), exact `cubic-bezier` curves, scroll triggers, and stagger choreography documented in Section 9 of `DESIGN_SYSTEM.md`.
- **Accessibility guidance** → Semantic markup, ARIA attributes, contrast, and keyboard behavior.

Evidence handling:
- `Verified` values should be implemented exactly as documented.
- `Observed` values should be followed unless stronger project evidence contradicts them.
- `Estimated` values may be used as starting points and refined through visual comparison.
- `Unknown` values must not be represented as facts. Choose a conservative, consistent implementation and record the decision as an implementation assumption.

If a reference URL is supplied, use it to resolve ambiguities and validate the design system. Do not silently change documented values merely to make the result look fashionable or more modern.

## 5. Implementation plan

Before coding, form a concise plan:

1. Map requested pages to existing routes or define the minimal route structure.
2. Migrate and organize reusable assets from `./design-system-assets/` (and source any missing client-specific media) into the project's asset directory.
3. Establish global tokens, fluid sizing variables, `z-index` layers, `@keyframes`, and typography.
4. Set up the required animation utilities or scroll/motion libraries.
5. Build the shared application shell (header, navigation, mobile drawer, footer, page container).
6. Build reusable primitives, media wrapper components, and UI components.
7. Implement page sections and route-specific composition with client copy and media.
8. Implement responsive transformations across desktop, tablet, and mobile.
9. Wire up interactions, hover micro-interactions, and scroll-driven animations.
10. Run checks and browser QA, then fix the highest-impact mismatches.

Prefer a small, coherent component system over duplicated page-specific markup.

## 6. Design fidelity requirements

### A. Tokens and Visual Effects First

Implement documented tokens centrally, preferably as CSS custom properties or the project's existing theme mechanism.

Include, where documented:
- Colors, semantic color roles, and linear/radial/conic/mesh gradients
- Font families, weights, and fluid type scale (`clamp()`)
- Spacing scale and section vertical rhythm
- Container widths, grid gaps, and `z-index` scale
- Border widths, colors, and subtle inner/gradient borders
- Radius scale
- Shadows, elevation, `backdrop-filter` (glassmorphism/blur), `mix-blend-mode`, and noise/grain overlays
- Breakpoints
- Motion durations, stagger steps, and exact `cubic-bezier(...)` easing curves

Do not scatter repeated literal values throughout the code when a shared token exists.

### B. Typography & Multilingual / RTL Support

- Load the correct local font files from `./design-system-assets/fonts/` or remote font providers when available and permitted.
- Match font weights, line heights, letter spacing, and responsive/fluid sizes.
- Preserve text hierarchy and optimal reading line lengths (`max-width: 60ch–75ch` where applicable).
- Support language direction and font fallback correctly.
- **For Arabic / RTL clients**: Set `dir="rtl"` and `lang="ar"` intentionally at the document or layout root, use high-quality Arabic typography (either specified in the design system or appropriate modern Arabic fonts like Readex Pro, IBM Plex Sans Arabic, Cairo, or Tajawal), and use CSS logical properties (`margin-inline`, `padding-inline`, `inset-inline`, `text-align: start`) instead of scattered physical left/right overrides. Flip directional icons (arrows, chevrons) appropriately in RTL.

### C. Layout, Page Composition, and Media Placement Architecture

- Match container widths, section order, grid/bento structures, whitespace, and alignment.
- Recreate the shared shell consistently across routes.
- Use semantic HTML landmarks (`<header>`, `<nav>`, `<main>`, `<section>`, `<aside>`, `<footer>`) and proper heading hierarchy.
- Avoid arbitrary absolute positioning for primary page layout; reserve absolute/fixed positioning for documented decorative layers, badges, and sticky elements.
- **Implement Media Placement Mechanics faithfully** (from Section 8 of `DESIGN_SYSTEM.md`):
  - Wrap images, videos, and canvases in containers with the documented `aspect-ratio`, `border-radius`, and `overflow: hidden`.
  - Apply exact `object-fit` (`cover`, `contain`) and `object-position` focal points.
  - Apply documented visual treatments: gradient scrims/overlays (`::before`/`::after`) behind foreground text to guarantee readability, CSS `filter`, `backdrop-filter`, `mix-blend-mode`, `clip-path`, and `mask-image` (such as radial/linear edge fade-outs).
  - Recreate device mockups, browser frames, glowing borders, or 3D perspective tilts (`transform: perspective(...) rotateX(...)`) when specified by the design system.
  - Configure `<video>` elements with documented attributes (`autoplay`, `loop`, `muted`, `playsinline`, `poster`, `preload`) and configure images with appropriate `loading="lazy"` or `fetchpriority="high"` on hero assets.

### D. Components

Build reusable components for repeated patterns. Follow the documented anatomy, variants, sizes, and states.

For each interactive component, implement relevant states:
- Default
- Hover
- Focus-visible
- Active/pressed
- Disabled
- Loading
- Error/invalid
- Selected/expanded

Do not make controls decorative if the design implies an action. Buttons, links, forms, menus, tabs, accordions, dialogs, carousels, and navigation should work to the extent required by the task.

### E. Responsive Implementation

Use the documented breakpoints where available. Test at the design-system viewports and at least:
- Desktop: approximately 1440px wide
- Tablet: approximately 768px wide
- Mobile: approximately 390px wide

Check:
- Navigation collapse and mobile menu/drawer transitions
- Grid and column collapses or reordering
- Typography and spacing scaling
- Media aspect-ratio shifts, responsive crops (`<picture>` / `srcset`), or hiding of heavy decorative assets on mobile
- Overflow and horizontal scrolling (e.g., touch carousels with `scroll-snap-type`)
- Touch target sizes (minimum `44x44px` where practical)
- Sticky/fixed elements and modal/drawer placement

Do not merely shrink desktop content. Implement the documented mobile composition.

### F. Motion, Choreography, and Animation Mechanics

Implement the exact animation mechanics documented in Section 9 ("Interaction, Motion & Animation Mechanics") of `DESIGN_SYSTEM.md`:

- **Animation Engine Setup**: If `DESIGN_SYSTEM.md` identifies a specific library (e.g., `gsap` + `ScrollTrigger`, `framer-motion`, `lenis` smooth scroll, `lottie-web`) and it fits the project stack, install or reuse it cleanly. Otherwise, implement the documented pure CSS `@keyframes`, transitions, and `IntersectionObserver` equivalents.
- **Exact Timing & Curves**: Use the documented `--duration-*` and `cubic-bezier(...)` tokens. Never substitute signature spring or exponential curves with flat `linear` or default `ease` transitions.
- **Entrance & Scroll Choreography**: Follow the "How It Works & How to Rebuild" recipes step by step—implement initial hidden states (e.g., `opacity: 0; transform: translateY(24px)`), viewport-entry triggers, sibling stagger delays, sticky/pinned scroll sections, parallax transforms, and infinite marquee loops.
- **Micro-interactions**: Implement documented hover/focus effects such as button elevation (`translateY`), icon directional slides (`translateX`), card border illumination, and image zoom-on-hover (`scale()`).
- **Reduced Motion**: Always implement `@media (prefers-reduced-motion: reduce)` to disable heavy transforms/scroll-jacking while preserving instant opacity/state visibility.

### G. Accessibility

- Use semantic elements and accessible names (`aria-label`, `aria-labelledby`).
- Ensure full keyboard operation (`Tab`, `Enter`, `Space`, `Escape` for modals/menus) and visible `:focus-visible` outlines.
- Associate form labels and validation messages.
- Provide meaningful `alt` text for informative images and `aria-hidden="true"` for decorative SVGs/backgrounds.
- Maintain adequate contrast over media using documented scrims/overlays.
- Do not claim formal WCAG conformance unless an actual audit has been performed.

## 7. Content, Client Branding, and Media Sourcing

When building the website—whether reproducing the reference or building for a specific client based on `DESIGN_SYSTEM.md`—handle assets and media systematically:

### 1. Client Brand & Copy Adaptation
- If building for a new client, apply the client's brand name, copywriting, value propositions, domain terminology, and (if requested) custom brand color overrides while strictly preserving the layout architecture, spacing, component anatomy, media framing, and animation mechanics of `DESIGN_SYSTEM.md`.
- If user-provided copy is incomplete, write high-conversion, domain-authentic copy tailored to the client's specific industry (never leave raw `Lorem ipsum` unless explicitly requested).

### 2. Leveraging Extracted Assets (`./design-system-assets/`)
- Consult the **Local Asset Manifest** in Section 8 of `DESIGN_SYSTEM.md`.
- Copy reusable structural and decorative assets—such as UI icons (`.svg`), arrows, background grid/mesh patterns, noise textures, Lottie animations (`.json`), and permitted fonts—from `./design-system-assets/` into the target project's `public/` or `src/assets/` folder and wire them into the components.
- Avoid using emoji as substitutes for documented SVG icons.
- If building for a new client, do not reuse the reference website's proprietary company logo or trademarked product screenshots unless explicitly authorized by the user.

### 3. Sourcing Missing Client Photos & Videos (Media Acquisition Hierarchy)
When building for a client who has not supplied all required photography, videos, or product visuals, **never leave broken image links, empty containers, or plain gray boxes**. Follow this exact hierarchy to populate the media wrappers:

- **Tier 1 — Client-Supplied & Extracted Reusable Assets**: Use any logos, product photos, or videos provided by the user alongside the structural SVGs/icons from `./design-system-assets/`.
- **Tier 2 — Media MCP Tools or Stock APIs (Preferred for Realistic Media)**:
  - If an image/video search MCP tool (e.g., Unsplash, Pexels) or generation tool is callable, or if API keys exist in the environment, search for and download high-resolution, niche-matching images (`.webp`/`.jpg`) and background loop videos (`.mp4`) directly into the project's local assets folder (e.g., `public/assets/images/`, `public/assets/videos/`).
  - Match the visual mood, lighting (dark/light mode compatibility), and exact `aspect-ratio` specified in `DESIGN_SYSTEM.md`.
- **Tier 3 — Direct Curated Stock Fetching via Shell / URLs**:
  - If no dedicated media MCP is present, use `curl` or reliable, high-availability stock URLs (such as curated Unsplash/Pexels direct media URLs with explicit sizing parameters like `?auto=format&fit=crop&w=1600&q=85`) tailored to the client's exact industry (e.g., medical clinic, e-commerce store, SaaS, real estate). Prefer downloading them locally into the project so offline/local builds never break.
- **Tier 4 — Custom-Engineered Interactive UI Mockups & SVG Artwork**:
  - When a section calls for a software dashboard, analytics card, or abstract visual and no screenshot is supplied, build a rich, interactive HTML/CSS component mockup or multi-layered SVG illustration using the design system's tokens, glassmorphism, and micro-animations rather than inserting an unrelated stock photo.

Document all newly sourced or generated media files clearly in your final report so the client knows which assets are stock/generated placeholders ready to be swapped with their own photography later.

## 8. Browser validation and visual comparison

When Chrome DevTools MCP is available:

1. Start the project using its existing documented development command. Do not guess the package manager; inspect lockfiles and scripts.
2. Wait for the server to be ready using supported tools or output. Do not claim it is running until confirmed.
3. Open the local implementation in the browser.
4. If a reference URL exists, inspect both reference and local implementation at matching viewport sizes (`1440px`, `768px`, `390px`).
5. Capture screenshots for every requested route and the main responsive viewports.
6. Compare and verify:
   - Overall composition, grid alignment, and section order
   - Typography, fluid sizing, line wrapping, and RTL/LTR directionality
   - Color tokens, gradients, glassmorphism (`backdrop-filter`), and surface treatments
   - Spacing, padding, and vertical rhythm
   - Media loading (zero broken images/videos), `object-fit` cropping, aspect ratios, masks, and overlays
   - Borders, radius, and shadows
   - Entrance animations, scroll-triggered effects, and hover micro-interactions
   - Navigation and interactive component states
7. Inspect browser console errors and failed network requests (`404` assets) where tools support it, and fix any broken asset paths immediately.
8. Fix mismatches in this order:
   - Broken assets, console errors, or structural/layout errors
   - Typography and sizing
   - Spacing and alignment
   - Media framing, masks, and overlays
   - Colors, gradients, and surfaces
   - Borders, shadows, and details
   - Motion, scroll choreography, and micro-interactions
9. Repeat screenshots after meaningful fixes.

Never claim pixel-perfect equivalence. Describe the observed degree of similarity and remaining differences honestly.

If the reference website is unavailable, use `DESIGN_SYSTEM.md` as the source of truth and validate the local implementation against every checklist item.

- Any existing component or end-to-end tests

- Shared navigation, mobile menu, and footer work.

- Responsive layouts do not introduce unintended horizontal overflow.
- No obvious console/runtime errors remain.
